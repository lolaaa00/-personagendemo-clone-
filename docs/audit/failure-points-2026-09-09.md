# Failure Points — 2026-09-09

A sweep for operational failure points and unowned problems, across eleven parallel audits: money, async lifecycle, scheduler and publishing, auth and access control, data lifecycle, content safety, infrastructure and secrets, output quality, database cost, the engine route, and the browser client.

Everything here was verified against the running system or the working tree. Production reads were taken live; nothing is inferred from docs or from the knowledge graph. Where a claim from an audit did not survive checking, it is recorded below as corrected rather than dropped, because the correction is part of the evidence.

Context for anyone reading this later: at the time of the sweep the platform had generated nothing since 2026-09-01, credits were in `enforce`, Stripe was dormant, and four social connections were live. Most of what follows is latent rather than burning, and the pilot starting is what converts it.

---

## The finding that outranks the individual bugs

**Six checks in this codebase could not fail, and four of them were cited as evidence that something was safe to turn on.**

| # | Check | Why it could not fail | Status |
|---|---|---|---|
| 1 | Billing reconciliation | Filters `key_source='platform' AND credits > 0`; every one of the 643 generation events predates those columns, so the input set was empty and "0 mismatches" was arithmetic on nothing. Enforced credits went live partly on this being green. | **Fixed** — `/api/health` now reports the denominator: `ok: N events examined`, or `idle: no billable events in the last 24h` |
| 2 | Live smoke, 25/25 | Sends `deliver:'review'`, which never enters the publish branch. It passed continuously while the publish gate was missing, and was cited as proof the gate was closed. | **Fixed** — the run now prints what it did **not** reach and why |
| 3 | `/api/health` | Seven of nine checks are advisory strings; only two can set `healthy = false`. It returns 200 "ok" while its own body reports pending migrations, a degraded billing schema, dropped activity events, or reconciliation **mismatches**. | Open |
| 4 | Scheduler check | `checks.scheduler` reads `RUN_SCHEDULER` — an environment variable, not whether the tick is alive, the lease is held, or `startScheduler` bailed on placeholder credentials. A wedged scheduler reports healthy. | Open |
| 5 | Metering audit spec | Asserts at **file** level: one `recordCostEvents(` anywhere in a 4,300-line file passes the whole file. `content/generate.ts` can never fail it again regardless of what is added. | **Fixed** — now asserts per call site |
| 6 | A persona-contract test | Had encoded the bug as expected behaviour, which is why a green suite never caught a latent whole-section data loss. | **Fixed** by its owner |
| 7 | **Storage-orphan audit by `owner`** | `storage.objects.owner` is **NULL on all 307 rows** — every upload goes through the service role, so the column is never set. Any orphan check keyed on ownership returns zero forever, while the leak continues. Path prefix (`<userId>/`) is the only honest key. | Open (method, not code) |

The shape is the same every time: **a question nobody could get a "no" from.** The rule that falls out of it, and the one already applied to 1 and 2:

> Assert the sample size, not just the result. A check that reports "ok" should report what it examined, and a run that examined zero instances of its subject is a failure, not a pass.

This is the cheapest durable fix in this document, and it applies to 3, 4 and 5 unchanged.

## The search key that found the two worst findings

Both of the most serious findings in this document were places where **the code contradicted a promise the product makes in writing to a customer**: the pricing page says "You approve before it posts" while the generation route never read the persona's autonomy setting, and the deletion flow says data is gone while nothing deleted stored media.

That is a searchable class, and a better key than severity: **take each written claim and find the line that must enforce it.** A claim with no enforcing line is either false or unverifiable, and both are worth knowing. It is cheap to run, it produces findings a customer would actually feel, and unlike a general sweep it has an obvious stopping point — the list of things the product says about itself is finite.
